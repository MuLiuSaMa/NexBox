# 排查笔记：GGOS / PowerX 电源计划为什么导不进来

日期：2026-11-21
性质：过程记录（我实际怎么想、怎么试、错在哪），不是结论文档。结论与改法见 [`2026-11-21-power-plan-import-fix.md`](./2026-11-21-power-plan-import-fix.md)。

---

## 0. 起点：先让代码能编译

第一条消息只有一个编译错误：`format!("HKCU\\{}\{}")` 里第二个分隔符没有转义。这本身没有信息量，但它给了我两个线索：这个文件在工作区里是**未提交的改动**（有人在写电源计划这块），而且报错位置正好在"导入失败后的兜底"函数里——说明用户已经在处理这个问题了。

修掉、`cargo check --lib` 过、全 crate 扫一遍没有同类写法之后，我才去看行为问题。这里的原则是：**没有可编译基线，一切运行时猜测都是浮沙。**

## 1. 拆报错：一条弹窗里其实躺着两条管线

弹窗文案是这种结构：

```
导入电源计划失败: {first_err}
（已自动移除本机不支持的电源设置项后重试，仍失败: {retry_err}）
```

这直接说明：**第一次导入失败了，然后代码做了一次"清理后重试"，重试也失败了**。所以不是"一个错误"，而是"两种不同的拒收理由"。这决定了排查方向——不能只盯着第二条看，得分别解释为什么第一次和第二次都被拒。

读 `import_plan_file` 与 `sanitize_power_plan_file` 后，管线的形状清楚了：

1. `powercfg /import 原文件`
2. 失败则 `reg load` 挂载 → 复制到 HKCU 临时键（删掉本机不存在的组/项、4 字节 `REG_BINARY` 改 `REG_DWORD`）→ `reg save` 成新 hive → 再 `/import`

## 2. 第一个假设：权限/路径/文件坏了——逐个证伪

我一开始的直觉是"管理员权限不够"或"路径有空格/中文"。逐条打掉：

| 实验 | 预期 | 实际 | 结论 |
| --- | --- | --- | --- |
| `net session` / 写 `HKLM\Software` | 判断是否管理员 | 非管理员，`HKLM` 拒绝访问 | 确认当前 shell 非提权 |
| `powercfg /import ACMEPCAMD.pow` | 若无权限应报拒绝访问 | **导入成功**，还打印了新 GUID | `powercfg /import` 不需要提权，权限假设不成立 |
| `powercfg /export` 同一计划 | 应该也能跑 | `0x522 客户端没有所需的特权` | 导出才需要提权，导入不需要——两者权限模型不同 |
| 文件头/大小检查 | 坏文件 | 六个 `.pow` 全是 `regf`，大小为 4096 整数倍 | 不是损坏 |
| 文件不存在 / 文本改后缀 | — | 分别是 `找不到该文件` / `0x3f8 注册表 I/O` | 报错是分层的，`找不到该文件` 是**特定**失败，不是万金油 |

其中第二步是关键：它同时否掉了"权限"和"工具坏了"，把问题锁定在**文件内容**上。

## 3. 把错误文案当数据，而不是当描述

中文 Windows 的错误文案很容易骗人。`找不到该文件` 听起来像"磁盘上没有这个文件"，但注册表 API 里 `ERROR_FILE_NOT_FOUND` 恰恰也是**"查不到这个值/键"**的返回码。也就是说，这个错误完全可以由 hive 内容触发。

这一步我没法直接证明（文件确实存在，报错却和路径不存在时一模一样），所以我把它降级成"能用一句话解释所有观察的假设"，并且**不让后续方案依赖它**。这也是后面选"重建"而不是"精确修补"的原因之一：我不能确定到底哪一项触发了哪个错误码，那就别赌。

## 4. 差分诊断：拿能导入的那份做对照组

手里有六份文件，其中一份能进、两份不能。这是最省力的实验设计——不用猜，直接对比"有"和"没有"。

`reg load` 只能挂 `HKLM`/`HKU`，非管理员直接堵死；`HKCU` 试过，报"根项必须是 HKLM 或 HKU"。于是我换成**离线读 hive**：

1. 先试 `pip install regipy`——pip 自身坏了（`ImportError: cannot import name 'SeparateBodyFileCache'`），死路。
2. 用 `uv venv` + `uv pip install regipy` 五秒解决。**工具链坏了就换一条，不要在坏的那条上修。**

然后对照本机 `HKLM\...\Power\PowerSettings`（系统认识的所有组/设置项）做集合差：

| | 本机不存在的组 | 本机不存在的设置项 | 类型异常 | 空设置键 |
| --- | --- | --- | --- | --- |
| ggOS | — | 1 | 2 处 4 字节 `REG_BINARY` | 1 |
| PowerX | 1 | 2 | 3 处 | — |
| ACMEPCAMD（能进） | — | — | — | — |

相关性非常干净：**能进的那份零异常，进不去的两份都有"系统不认识的 GUID"和"类型写坏的值"**。到这里，"hive 里有本机不认识的东西"这个方向基本成立。

## 5. 外部证据补上最后一环

本地只能推出"内容不合规"，推不出"为什么旧版本能进、现在不能"。搜了一下，命中一个同型号的案例：26H2（26300.9550）上自定义 `.pow` 导入报「指定的值存在格式错误，或者不在目标电源设置的范围内」，25H2 同文件正常。本机正好是 `10.0.26300.10075`。

这解释了第二段错误：26H2 把导入变成了**整份事务的逐项校验**，而旧兜底只是把"系统不认识的项"删掉、把类型改对，仍留有边角（空设置键、组级值），于是依旧被整份拒绝。

## 6. 死胡同记录（都是真实花掉的时间）

1. **想离线复刻旧兜底**：需要 `reg save`，它要 SE_BACKUP，非管理员报"客户端没有所需的特权"。HKCU 也一样。死。
2. **认真考虑过自己写 hive 生成器**：`regf`/`hbin`/`nk`/`vk` 格式写起来不算难，但唯一的验证手段是 `powercfg /import` 的黑盒报错，等于盲改。放弃——**能用受支持的 API 表达的状态，不要用二进制手工拼**。
3. **`cmd //c "powercfg ..."` 在 git bash 里根本没执行**：它只打印了 cmd 的 banner 就返回，退出码还是 0，一度以为"命令跑了但没输出"。后来改成直接 `powercfg` + 单独处理路径才干净。Windows 上跨 shell 调命令行工具，失败模式比想象的多。
4. **`windows-sys` 的 `HKEY` 是 `*mut c_void` 不是整数**，`PowerWriteACValueIndex(0, …)` 编译失败；同理 `uuid::as_fields()` 返回借用，直接接 `?` 会触发 E0716。都是小坑，但都在编译期暴露，成本可控。
5. **我自己的 Python 小脚本犯了和 Rust 那个错一模一样的毛病**：`"HKCU\Software\..."` 里的 `\S` 被当转义序列。修别人同一类 bug 的时候自己踩一遍，说明这类错误和语言无关，只和"路径字符串手写"有关。

## 7. 转折点：与其修坏掉的状态，不如重建目标状态

卡在"无法复刻旧兜底"时，我换了个问法：**我要的最终状态是什么？**——系统里存在一个计划，它的每个设置项都等于 `.pow` 里那个值。那就不必经过"坏 hive → 修好的 hive → 导入"，可以直接：

```
复制一份系统模板计划 → 逐项写入 .pow 里的值 → 改名
```

而且这条路径恰好还是**诊断工具**：如果这些值本身不合法，逐项写入时会一条条报错；如果一条都不报错，就证明"值没问题，被拒的是 hive 整体"。

在真机上用 Python 复刻跑了一遍：

- ggOS：提取 59 项，写入 **0 条被拒**；
- PowerX：提取 89 项，写入 **0 条被拒**；
- 写出的计划名称/描述正确，`PROCTHROTTLEMIN` 查回 `0x64` 与 `.pow` 一致。

这个结果把"要不要继续抠 hive"彻底关掉了：**值都能进，只有整份 hive 进不去。** 方案从"修补"变成"重建"。

## 8. 落地时的取舍（每个都是为了少一个失败模式）

- **只在直接导入失败后介入**：能进的文件仍走原生 `/import`，不改变现有成功路径的行为。
- **读取仍用 `reg load`，写入全走 API**：读取是一次性的、可以只读；写入用 `powrprof`（`powercfg /setacvalueindex` 的同一套底层），校验规则与系统一致，不存在"我以为合法"。
- **不生成任何 hive 文件**：旧路径的 `reg save`、临时 `.pow`、清理逻辑全部消失。
- **未知项跳过而不是报错**：目标是"尽量还原调校"，不是"完美复制文件"。
- **`REG_BINARY` 4 字节当 DWORD 读**：这就是两份文件里最常见的那种写坏，读的时候顺手归一化。
- **基础模板按序挑**：卓越性能 → 高性能 → 激活计划 → 第一条。第三方游戏计划基本都从这两个模板派生。
- **间接字符串还原**：内置计划的 `@powrprof.dll,-19,Ultimate Performance` 不能直接当名字写进去。
- **改名失败就删掉刚复制的计划**：不留重名垃圾。

## 9. 验证：分层，而不是"编译过了就算完"

1. **编译层**：`cargo check`（lib + bin）。
2. **危险原语层**：单独编了个小程序，直接调 `PowerDuplicateScheme` / `PowerWrite*ValueIndex` / `changename`，写 AC=42、DC=43，再用 `powercfg /query` 读回 `0x2a`/`0x2b`。这一步是为了证明 **GUID 字段序没搞错**——这类错误编译期永远发现不了，跑起来才发现"值写到了别的 GUID 上"。
3. **规则层**：Python 复刻验证"提取 + 过滤 + 写入"的项数与被接受率（就是第 7 节那张表）。
4. **交付层**：留下可复测的步骤（先删同名计划，再重建应用点导入），因为完整链路必须由真实应用跑一次才算数。

## 10. 收尾：不留痕迹

排查过程中我在用户的机器上创建过几份测试计划（`6d6fafcf…`、`d1a60810…`、`1230da5d…`、`79bc6b03…`、`a545d75c…`），全部 `powercfg /delete` 掉；临时注册表键 `HKCU\Software\NexBoxPowTest`、`HKLM\NexBoxPP*`、临时 `.pow`/`.reg`、venv、探针工程也都清干净。**在别人机器上做实验，进出要一样干净**——尤其这类会改系统电源方案的实验。

## 11. 这次可以抽出来的规则

1. **先让基线可编译，再谈行为**。
2. **一条报错里常常有多条失败**，先把管线拆开，别用一个假设解释两个错误。
3. **把本地化错误文案翻译回 Win32 错误码**再推理，中文文案的暗示经常是错的。
4. **一定要有对照组**：能工作的那个样例比任何文档都说明问题。
5. **权限拿不到就换观测手段**（离线解析、替代命令、把黑盒当验证器），不要卡在"必须提权才能复现"上。
6. **当验证器是黑盒且不可控时，选择用受支持的 API 重建状态，而不是修补二进制/文件结构**。
7. **风险最高的原语单独做探针**，别把它藏在完整流程里等运气。
8. **实验会改用户环境，就必须能原样撤回**。

## 12. 如果重来一次，哪里可以更快

- 一开始就该跑"能进的那份"，把对照组放在第一批实验里，而不是先花时间验证权限假设。
- `regipy` 那一步可以更早：拿到 hive 结构之后，"未知 GUID"是十分钟就能看出来的东西，不需要绕权限。
- 26H2 的检索应当更早做：知道"这是系统行为变化"之后，很多关于"文件写法"的猜测可以直接跳过。

---

一句话复盘：**这次真正解出问题的不是"读懂 hive 格式"，而是先把它当成一个黑盒差分问题——找出"能进/不能进"的唯一结构性差异，再用系统的公开接口重建出等价状态。**
